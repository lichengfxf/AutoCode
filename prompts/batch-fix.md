# 修复阶段（批处理模式）

**重要提示：这是自动化流程的第4步（共4步：规划 → 执行 → 评审 → 修复）**
- 这里没有人工介入 - 自动修复评审发现的问题
- 不要提问或请求批准 - 只修复问题
- 直接、实事求是 - 不需要客套话

阅读 .task 文件中的 REVIEW_RESULT。按优先级修复问题。

## 没有需要修复的？在这里停止。
如果评审显示：
- 所有 OUTCOMES_ACHIEVED: yes
- 没有 ENVIRONMENT_ISSUES（空或 "none"）
- 没有 BLOCKERS（空或 "none"）
- 没有 ISSUES（空或 "none"）

那么你没有任何事要做。只需：
1. 删除 .task 文件
2. 确保所有批处理任务在 TASKS.md 中标记为 `- [x]`
3. 立即停止 - 不要实现新代码，不要开始新任务

修复阶段**只**修复评审发现的问题。它**不**：
- 实现新功能
- 开始下一个任务
- 添加评审未标记的改进
- 做超出修复标记问题以外的任何事情

如果没有问题，你的整个工作是：删除 .task文件，标记所有完成，完成。

## 优先级顺序（仅当存在问题时）
1. ❌ 结果未达成 - 任务未完成！先修复实现。
2. 🔧 环境问题 - 创建修复任务
3. 🔴 BLOCKERS - 必须修复的代码问题
4. 🟡 问题 - 如果直接就修复
5. 🟢 建议 - 仅当琐碎时修复

## 如果任何结果未达成
实现没有完成任务要求。你必须：
1. 从 .task文件 阅读 EXPECTED_OUTCOMES 和 OUTCOMES_ACHIEVED
2. 找出每个失败结果未达成的原因
3. 修复实现直到**所有**结果都达成
4. 在继续之前自己重新验证结果
这不是可选的 - 没有结果的任务未完成。

## 处理环境问题（关键！）
环境问题是可解决的。你必须：
1. 从 .task 文件阅读 REMEDIATION
2. 向 TASKS.md 添加新任务以修复环境问题
   - 将其插入当前任务**之前**（以便下次迭代运行）
   - 格式：`- [ ] Setup: [修复操作]`
3. 将当前任务取消标记回 `- [ ]`（环境修复后它们会重试）
4. 删除 .task 文件
5. 不要标记为阻塞 - 环境任务会修复它

## 你对代码问题的工作
1. 修复BLOCKERS（必须）
2. 修复问题（应该修复）
3. 考虑建议（最好有）
4. 重新运行 TEST_COMMAND 确认
5. 提交修复："fix: [描述]"

## 永远不要在测试上作弊
当测试失败时，你必须修复实现，而不是测试。

**禁止的"修复"实际上是作弊：**
- Mock 返回值使测试通过
- 削弱断言（将 `toBe(5)` 改为 `toBeTruthy()`）
- 删除失败的测试用例
- 添加 `.skip` 或注释掉失败的测试
- 将被测试的函数 stub 为返回预期值

**唯一可以更改测试的情况：**
- 测试本身有 bug（错误的期望值、拼写错误）
- 上游更改使测试的假设无效（API 更改、架构更改）
- 并且你验证测试在更改后仍然测试有意义的行为

## 修复后
如果所有修复 + 测试通过：
- 删除 .task 文件
- 确保所有批处理任务在 TASKS.md 中标记为 `- [x]`（如果有用则添加备注）

如果发现环境问题：
- 向 TASKS.md 添加修复任务（见上文）
- 取消标记当前任务
- 删除 .task 文件
- 继续（未阻塞！）

如果真正的代码BLOCKERS（罕见 - 只有无法修复的安全/数据问题）：
- 将 TASKS.md 中的任务取消标记回 `- [ ]`
- 添加BLOCKERS备注：`- [ ] 任务描述 ⚠️ 被阻塞：[原因]`
- 保留 .task 文件作为上下文
