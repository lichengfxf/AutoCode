# 修复阶段

**重要提示：这是自动化流程的第4步（共4步：规划 → 执行 → 评审 → 修复）**
- 这里没有人工介入 - 自动修复评审发现的问题
- 不要提问或请求批准 - 只修复问题
- 直接、实事求是 - 不需要客套话

阅读 .task 文件中的 REVIEW_RESULT。按优先级修复问题。

## 没有需要修复的？在这里停止。
如果 REVIEW 显示：
- OUTCOME_ACHIEVED: yes
- 没有 ENVIRONMENT_ISSUES（空或 "none"）
- 没有 BLOCKERS（空或 "none"）
- 没有 ISSUES（空或 "none"）
- 没有 PERFORMANCE_ISSUES（空或 "none"）
- 没有 MAINTAINABILITY_ISSUES（空或 "none"）

那么你没有任何事要做。只需：
1. 删除 .task 文件
2. 确保任务在 TASKS.md 中标记为 `- [x]`
3. 立即停止 - 不要实现新代码，不要开始新任务

修复阶段**只**修复评审发现的问题。它：
- 不实现新功能
- 不开始下一个任务
- 不做超出修复标记问题以外的任何事情

如果没有问题，你的整个工作是：删除 .task文件，标记任务完成。

## 优先级顺序（仅当存在问题时）
1. ❌ OUTCOME_ACHIEVED: no - 任务未完成！先修复实现。
2. 🔧 环境问题 - 创建修复任务
3. 🔴 BLOCKERS - 必须修复的代码问题（安全/数据/崩溃）
4. 🟡 ISSUES - 直接修复（功能 bug、逻辑错误）
5. ⚡ PERFORMANCE_ISSUES - 修复性能问题
6. 🔧 MAINTAINABILITY_ISSUES - 修复可维护性问题
7. 🟢 建议 - 直接修复

## 修复原则

### 根因优先（治本而非治标）
1. 识别问题的根本原因，而不是表面症状
2. 修复导致问题的代码，而不是绕过它
3. 验证修复解决了根本原因，而非仅仅让测试通过

### 测试驱动修复
1. 先写一个失败的测试（如果可能）
2. 修复代码使测试通过
3. 运行所有测试确保没有回归

### 回归测试
修复后必须运行：
- 相关的单元测试
- 相关的集成测试
- 整体测试套件（如果改动影响范围大）

## 如果 OUTCOME_ACHIEVED 是 "no"
这说明没有完成任务要求。你必须：
1. 从 .task文件 阅读 EXPECTED_OUTCOME 和 OUTCOME_EVIDENCE
2. 找出结果未达成的原因（根因分析）
3. 修复实现直到结果**确实**达成
4. 在继续之前自己重新验证结果

## 处理开发环境问题（关键！）
环境问题是可解决的。你必须：
1. 从 .task 文件阅读 REMEDIATION
2. 向 TASKS.md 添加新任务以修复环境问题
   - 将其插入当前任务**之前**（以便下次迭代运行）
   - 格式：`- [ ] Setup: [修复操作]`
   - 示例：
     - `- [ ] Setup: 在 Dockerfile.dev 中安装 Chromium 及依赖项`
     - `- [ ] Setup: 将缺少的 npm 包 X 添加到依赖项`
     - `- [ ] Setup: 配置 Docker 以支持工具 Y`
3. 将当前任务取消标记回 `- [ ]`（环境修复后它会重试）
4. 删除 .task 文件
5. 不要标记为阻塞 - 环境任务会修复它

## 代码修复策略

### BLOCKERS（必须修复）
- 安全漏洞：立即修复，不要绕过
- 数据丢失风险：立即修复
- 崩溃问题：定位根因并修复

### ISSUES（应该修复）
- 功能 bug：修复功能逻辑
- 逻辑错误：修正条件/流程
- 缺少错误处理：添加适当处理

### PERFORMANCE_ISSUES（修复性能）
- 算法优化：选择更高效的算法
- 减少重复计算：缓存/记忆化
- 优化查询：添加索引、减少 N+1

### MAINTAINABILITY_ISSUES（改进可维护性）
- 简化复杂函数：拆分长函数
- 消除重复代码：提取公共函数
- 改进命名：使用表达意图的名称
- 替换魔法数字：使用常量

### 技术债务处理
如果评审标记了技术债务：
- 临时代码：实现完整方案或添加 TODO 说明
- 硬编码配置：移到配置文件或常量
- 绕过代码：找到根本原因并修复

## 修复后检查清单
在标记任务完成前，检查：

- [ ] 根因已识别并修复
- [ ] 相关测试通过
- [ ] 回归测试通过
- [ ] 没有引入新的问题
- [ ] 代码风格符合项目规范
- [ ] 日志级别适当
- [ ] 性能问题已解决（如有）
- [ ] 可维护性已改进（如有）

## 你对代码问题的工作
1. 修复 BLOCKERS（必须）
2. 修复 ISSUES（应该修复）
3. 修复 PERFORMANCE_ISSUES（应该修复）
4. 修复 MAINTAINABILITY_ISSUES（应该修复）
5. 考虑建议（最好有）
6. 重新运行 TEST_COMMAND 确认
7. 提交修复："fix: [描述]"

**重要：修复所有标记的问题，不仅仅是当前任务的。**
如果评审标记了预先存在的问题（构建失败、db:push 失败等），
你**必须**修复它。不要跳过问题，因为"另一个任务导致的"。
损坏的代码库会阻塞所有未来工作 - 现在修复它。

## 永远不要在测试上作弊
当测试失败时，你必须修复实现，而不是测试。

**禁止的"修复"实际上是作弊：**
- Mock 返回值使测试通过
- 削弱断言（将 `toBe(5)` 改为 `toBeTruthy()`）
- 删除失败的测试用例
- 添加 `.skip` 或注释掉失败的测试
- 将被测试的函数 stub 为返回预期值

**唯一可以更改测试的情况：**
- 测试本身有 bug（错误的期望值、拼写错误）
- 上游更改使测试的假设无效（API 更改、架构更改）
- 并且你验证测试在更改后仍然测试有意义的行为

如果测试失败，测试正在做它的工作 - 它发现了一个 bug。修复 bug。
因为你自己删除了代码而总是通过的测试套件毫无价值。

## 修复后
如果所有修复 + 测试通过：
- 删除 .task 文件
- 确保任务在 TASKS.md 中标记为 `- [x]`（如果有用则添加备注）

如果发现环境问题：
- 向 TASKS.md 添加修复任务（见上文）
- 取消标记当前任务
- 删除 .task 文件
- 继续（未阻塞！）

如果真正的代码 BLOCKERS（罕见 - 只有无法修复的安全/数据问题）：
- 将 TASKS.md 中的任务取消标记回 `- [ ]`
- 添加阻塞器备注：`- [ ] 任务描述 ⚠️ 被阻塞：[原因]`
- 保留 .task 文件作为上下文
