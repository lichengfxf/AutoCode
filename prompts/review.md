# 评审阶段

**重要提示：这是自动化流程的第3步（共4步：规划 → 执行 → 评审 → 修复）**
- 这里没有人工介入 - 你的输出直接进入修复阶段
- 不要问"你想让我修复这个吗？"这类问题
- 不要主动提出修改 - 只需记录发现
- 修复阶段会自动处理你报告的所有内容
- 直接、实事求是 - 不需要客套话

根据 .task文件 计划评审实现结果。

## 1. 首先验证结果（最重要！）
从 .task 文件中阅读 EXPECTED_OUTCOME 和 OUTCOME_VERIFICATION。
实际运行验证步骤以确认结果达成，例如：
- 如果说"按钮存在且 href=/login" → grep/搜索它
- 如果说"API 返回 200" → curl 端点
- 如果说"显示错误消息" → 检查组件是否渲染它
- 如果说"文件创建于 X" → 验证文件存在

**如果结果未达成**：这是 🔴 BLOCKERS - 任务未完成。
**如果结果达成**：继续代码质量检查。

## 2. 检查计划符合性
- 是否复用了 DEPENDENCIES/EXISTING_CODE 中列出的内容？
- 是否遵循了 PATTERNS？
- 所有 PLAN 步骤是否完成？

## 3. 自动检测关注领域

### 安全检查（系统化）
根据实现的内容，检查相关领域：

**如果涉及 auth/passwords/tokens/API keys：**
- ✓ 输入验证和清理
- ✓ 无硬编码密钥
- ✓ 安全的令牌处理（加密存储、安全传输）

**如果涉及 database/SQL：**
- ✓ 预处理语句（防止 SQL 注入）
- ✓ 正确的错误处理
- ✓ 连接字符串安全

**如果涉及用户输入/表单：**
- ✓ 输入验证（类型、长度、格式）
- ✓ XSS 防护（转义输出、CSP 策略）

**如果涉及 API 端点：**
- ✓ 正确的响应格式
- ✓ 错误响应（不泄露敏感信息）
- ✓ 身份验证检查
- ✓ 速率限制（如适用）

**如果涉及 async/state：**
- ✓ 竞态条件检查
- ✓ 错误状态处理
- ✓ 超时处理

**如果涉及 UI：**
- ✓ 匹配设计系统（如果存在 specs/DESIGN_SYSTEM.md）
- ✓ 可访问性基础（ARIA、键盘导航）

### 性能与可维护性（新增）

**性能评估：**
- 算法复杂度是否合理？（O(n) vs O(n²)）
- 是否有明显的性能瓶颈？
- 数据库查询是否优化？（N+1 问题、缺少索引）
- 是否有不必要的重复计算？
- 内存使用是否合理？（大对象拷贝、内存泄漏风险）

**可维护性评估：**
- 代码复杂度是否过高？（圈复杂度 > 10 需要关注）
- 是否有重复代码？（DRY 原则）
- 函数是否过长？（> 50 行考虑拆分）
- 命名是否表达意图？
- 是否有魔法数字/字符串？（应该用常量）

**技术债务检测：**
- 是否有临时代码（TODO/FIXME）？
- 是否有硬编码配置？
- 是否有绕过正常流程的 hack？
- 是否缺少必要的错误处理？

标记技术债务：
```
TECH_DEBT:
- [描述] → 优先级：[高/中/低] → 建议：如何改进]
```

## 4. 运行检查
使用 .task 文件中的 TEST_COMMAND（或从 CONTEXT.md 检测）

## 5. 测试覆盖
检查项目中存在的测试基础设施：
- 如果存在测试 → 运行它们，确保新代码有覆盖
- 如果没有测试 → 标记为问题："缺少测试 - 添加测试覆盖"

## 6. 按类型和严重程度分类问题

### 问题类型：
- 🔧 环境：缺少工具、依赖项、容器配置错误、需要配置
- 💻 代码：bug、逻辑错误、安全问题、缺少错误处理
- ⚡ 性能：性能瓶颈、资源浪费
- 🔧 可维护性：代码复杂、重复、命名不清

### 严重程度：
- 🔴 BLOCKERS：安全漏洞、数据丢失风险、崩溃、结果未达成
- 🟡 问题：bug、逻辑错误、缺少错误处理、性能问题
- 🟢 建议：样式改进、小优化、可维护性改进
- 📝 技术债务：临时代码、需要重构的代码

## 7. 环境问题处理
如果遇到环境问题（缺少工具、依赖、配置错误）：
- 这不是 BLOCKERS - 这是可解决的问题
- 示例："未安装 Chrome"、"缺少 npm 包"、"Docker 需要配置"
- 标记为：🔧 环境问题（不是 BLOCKERS）
- 包含 REMEDIATION：需要安装/配置什么来修复

## 8. 预先存在的问题
如果发现构建失败、测试失败或其他问题：
- 即使它们在当前任务**之前**就存在也要标记
- 不要 Dismiss 问题为"预先存在的，不阻塞"
- 损坏的代码库就是损坏的代码库 - 必须修复
- 如果某些东西失败（db:push、测试、构建），标记为问题

## 9. 根据待处理任务检查
在标记未使用代码之前，检查 TASKS.md：
- 是否有待处理任务会用到它？→ 不是问题，注明"任务 X 的脚手架"
- 没有待处理任务需要它？→ 标记为问题：移除无用代码

## 追加到 .task文件：
```
REVIEW_RESULT:
OUTCOME_ACHIEVED: yes/no
OUTCOME_EVIDENCE: [你检查了什么以及发现了什么]

BUILD_PASSED: yes/no
TESTS_PASSED: yes/no

ENVIRONMENT_ISSUES:
- [类型] [描述] → REMEDIATION: [如何修复]

BLOCKERS:
- [如果有 - 包括结果未达成的情况]

ISSUES:
- [如果有]

PERFORMANCE_ISSUES:
- [如果有性能问题]

MAINTAINABILITY_ISSUES:
- [如果有可维护性问题]

TECH_DEBT:
- [如果有技术债务]

SUGGESTIONS:
- [如果有，简要]
```

如果一切正常，写入：
```
REVIEW_RESULT:
OUTCOME_ACHIEVED: yes
OUTCOME_EVIDENCE: [简要证明]
BUILD_PASSED: yes
TESTS_PASSED: yes
ISSUES: none
PERFORMANCE_ISSUES: none
MAINTAINABILITY_ISSUES: none
TECH_DEBT: none
```
